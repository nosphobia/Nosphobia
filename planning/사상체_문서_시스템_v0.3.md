# 사상체 문서 시스템

이 문서는 노스포비아 프로젝트의 *사상체 문서 작성·갱신·확정* 워크플로우와 그 도구 체계를 정의한다.

## 본 문서가 다루는 영역

- 사상체 문서를 *어떻게 만들고 갱신하고 확정하는가*의 작업 흐름
- 작업 흐름을 지원하는 *폴더 구조·파일 구조·도구·명령어*
- LLM·프로그램·사용자의 *역할 분담*

## 본 문서가 다루지 않는 영역 (별도 문서 참조)

- 사상체 문서의 *형식·표기·문체* — `사상체_정의.md`
- 사상체의 *세계관적 정의·관리국 구조* — `세계관_설정.md`
- 사상체 문서의 *콘텐츠 컨셉·캐릭터 톤* — `프로젝트_의도.md`
- *구체적 구현 코드* — 본 문서는 *기획 수준*에 집중한다. 구현 시점에 별도 작업

> 🚧 **마커 안내**
> `🚧 TBD` 표시가 붙은 영역은 *결정 대기 항목*이다.

---

## 1. 시스템 개요

### 1.1. 시스템의 목표

> *사용자가 사상체에 대한 컨셉·아이디어·레퍼런스 자료를 주면, LLM과 프로그램의 협력을 통해 `사상체_정의.md`의 규칙에 정합한 사상체 문서를 만들어주는 시스템.*

### 1.2. 설계 원칙

본 시스템은 다음 4가지 원칙의 균형 위에 설계된다.

| 원칙 | 의미 |
|---|---|
| **정합성** | 모든 산출물은 `사상체_정의.md` §7.4 자기 점검표를 통과해야 한다. |
| **자동화** | 단순·기계적 작업은 *프로그램*이, 창작·해석이 필요한 작업은 *LLM*이 담당한다. |
| **창작 자유도** | 시스템이 *형식의 강제*를 위해 *내용의 다양성*을 해치지 않는다. |
| **가역성** | 모든 작업은 *분해 → 수정 → 재통합*이 가능해야 한다. 원본 손실은 일어나지 않는다. |

### 1.3. 두 계층 워크플로우

본 시스템은 두 계층의 워크플로우를 가진다.

| 계층 | 입력 | 출력 | 목적 |
|---|---|---|---|
| **Tier 1** | `docs/raw/`에 작성된 사용자의 컨셉·레퍼런스 | `docs/entities/`의 새 사상체 문서 | *신규 사상체 정의* |
| **Tier 2** | `docs/entities/`의 기존 사상체 문서 | 갱신된 사상체 문서 | *기존 사상체 수정* |

두 계층은 *입력 단계만 다르고*, 그 이후의 *피드백 루프·확정 흐름은 동일*하다. 즉 *공유 단계*가 존재한다 (§3.3).

> **보류 항목**: 격리 절차·대응 지침을 *나폴리탄/격리픽션/규칙괴담 장르의 단편 콘텐츠*로 유통하는 워크플로우(가칭 *Tier 3*)는 §9.1로 보류한다.

### 2.2. 작업 단계별 폴더 역할

| 폴더 | 단계 | 역할 |
|---|---|---|
| `docs/raw/` | 원자재 | 사용자가 사상체 컨셉·레퍼런스를 자유롭게 서술. 형식 제약 없음. |
| `docs/docs/working/<순서코드>/` | 작업 중 | 5개 항목 파일 + 5개 피드백 파일. 피드백 루프가 일어나는 공간. |
| `docs/entities/` | 확정 | 통합된 사상체 문서. *피드백을 받기 위한 것이 아니라 *읽히기 위한* 영역*. |
| `docs/entities/archive/` | 보관 | 구버전 사상체 문서. |

### 2.3. 항목 5요소

사상체 문서는 다음 5개 항목으로 분해된다.

| 항목 | 파일명 (예: 순서코드 `0341`) | 시스템 참조 |
|---|---|---|
| **개요** | `0341_개요.md` | 사상체_정의 §6.1 (frontmatter + 개요 표 + 파생 개체 + 설명) |
| **변칙 현상** | `0341_변칙현상.md` | 사상체_정의 §6.3 (변칙 현상 6요소 권장 골격) |
| **격리 절차** | `0341_격리절차.md` | 사상체_정의 §6.2 (규칙괴담 형식) |
| **대응 지침** | `0341_대응지침.md` | 사상체_정의 §6.2 (규칙괴담 형식) |
| **사건 기록** | `0341_사건기록.md` | 사상체_정의 §6.6, §6.7 |

**왜 5개인가**:
- 사상체_정의 §6.1의 *개요*는 *파생 개체*·*설명*을 모두 포함한다 (`## 개요` 산하의 `### 파생 개체`·`### 설명`).
- 본문 4항목(변칙 현상 / 격리 절차 / 대응 지침 / 사건 기록)은 각각 독립.
- 합계 5개.

**왜 순서코드 접두어를 붙이는가**:
- 작업 중 여러 사상체가 working/에 공존할 가능성 고려
- 파일을 열었을 때 *어느 사상체의 어느 항목인지*가 파일명만으로 즉시 식별
- IDE에서 파일 검색 시 *순서코드 prefix*로 한 사상체의 모든 파일을 빠르게 좁힐 수 있음

### 2.4. 피드백 파일 구조

각 항목마다 *피드백 파일이 1:1로 짝지어진다*. 즉 `0341_변칙현상.md`에 대한 피드백은 *오직* `0341_변칙현상_fb.md`에만 작성된다.

**피드백 파일 형식**:

```markdown
# <항목명> 피드백 (순서코드: <순서코드>)

## 처리 대기

- [ ] [태그] 피드백 내용
- [ ] [태그] 피드백 내용

## 처리 완료

- [x] [태그] 피드백 내용 — 처리일: YYYY-MM-DD
```

**태그**:

| 태그 | 의미 |
|---|---|
| `[창작]` | 새 내용 창작·기존 내용 재해석이 필요한 피드백. *모호한 지시* 포함. |
| `[정합]` | 형식·표기·문체 정합화 같은 기계적 변환 피드백. *명시적 지시* 포함. |

**처리 마킹 규칙**:
- 처리 대기 상태: `- [ ]`
- 처리 완료 상태: `- [x]`
- 처리 시점에 *처리 대기* 영역에서 *처리 완료* 영역으로 이동.
- 처리 완료 영역은 *기록 보존*용. 다음 갱신 시 LLM이 *이전에 어떤 피드백을 어떻게 처리했는지* 컨텍스트로 활용 가능.

## 3. 워크플로우

### 3.1. Tier 1 — 신규 사상체 정의

```
[1] 사용자 → docs/raw/<자유명>.md 에 컨셉·레퍼런스 작성
              ↓
[2] 사용자 → /doc-init <docs/raw/문서경로> <ID> 명령어 입력
              ↓
[3] LLM(Opus, doc-init-draft 스킬 활성화)
     → docs/raw/ 분석 + docs/working/<순서코드>/ 폴더 생성
       5개 항목 파일 + 5개 빈 피드백 파일 작성
              ↓
[4] 사용자 → 각 항목 검토 + 해당 피드백 파일에 수정 사항 작성
              ↓
[5] 사용자 → /doc-review <ID> 명령어 입력
              ↓
[6] LLM(현재 모델) → 5개 피드백 파일 읽기 → 해당 항목 갱신
                     처리된 피드백을 [x] 처리 + 처리 완료 영역으로 이동
              ↓
[7] (필요시 [4]~[6] 반복)
              ↓
[8] 사용자 → /doc-ig <ID> 명령어 입력
              ↓
[9] 프로그램 → validate (§7.4 자기 점검표 검증)
              ↓ (통과)
[10] 프로그램 → integrate (5개 항목 → 단일 사상체 문서)
              ↓
[11] 프로그램 → index-entities (사상체_목록.md 갱신)
              ↓
[12] docs/raw/ 원본은 archive로 이동, docs/working/<순서코드>/는 삭제
```

### 3.2. Tier 2 — 기존 사상체 수정

```
[1] 사용자 → /doc-div <docs/entities 문서경로> 명령어 입력
              ↓
[2] 프로그램 → decompose (단일 사상체 문서 → 5개 항목 파일 분해)
              docs/working/<순서코드>/ 폴더 생성 + 5개 빈 피드백 파일 작성
              원본 문서는 docs/entities/archive/로 이동
              ↓
[3] 사용자 → 각 항목 검토 + 해당 피드백 파일에 수정 사항 작성
              ↓
[4]~[ ] (이후 Tier 1의 [5]~[12]와 동일)
```

### 3.3. 워크플로우 간 공유 단계

Tier 1과 Tier 2는 *입력 단계만 다르고*, 다음 단계는 *완전히 동일*하다:

- 피드백 작성·갱신 루프 (`/doc-review`)
- 확정·검증·통합·인덱싱 (`/doc-ig`)

즉 슬래시 명령어 4개 중 2개(`/doc-review`, `/doc-ig`)는 *두 워크플로우 공용*. 나머지 2개(`/doc-init`, `/doc-div`)가 *입력 단계만 분기*.

## 4. 슬래시 명령어와 스킬

### 4.1. 슬래시 명령어 4개

| 명령어 | 인자 | 용도 | 스킬 사용 | 사용 모델 |
|---|---|---|---|---|
| `/doc-init` | `[문서경로] [ID]` | Tier 1 입력: docs/raw → docs/working 초안 | **doc-init-draft** | Opus |
| `/doc-div` | `<문서경로>` | Tier 2 입력: docs/entities 분해 → working | 없음 (순수 프로그램) | — |
| `/doc-review` | `<ID>` | 피드백 파일 읽고 항목 갱신 | 없음 (명령어 본문 직접 안내) | 현재 모델 |
| `/doc-ig` | `<ID>` | 검증 → 통합 → 인덱싱 | 없음 (명령어 본문 직접 안내) | Sonnet (검증 단계만) |

### 4.2. 스킬 사용 정책

본 시스템은 **`/doc-init`에만 스킬을 사용**한다. 나머지 3개 명령어는 *스킬 없이 명령어 본문 내에 작업 흐름을 직접 명시*한다.

**근거**:

| 명령어 | 작업 복잡도 | 체크리스트 필요성 | 결정 |
|---|---|---|---|
| `/doc-init` | **높음** — docs/raw 분석, 5개 항목 창작, §7.4 정합성 점검, 외부 자료 조사 가능 | **높음** | 스킬 |
| `/doc-div` | **낮음** — 순수 프로그램, LLM 미사용 | 없음 | 명령어만 |
| `/doc-review` | **중간** — 피드백 해석, 갱신 적용, 체크박스 마킹 | 중간 | 명령어만 (작업 흐름 직접 명시) |
| `/doc-ig` | **낮음** — 프로그램 도구 순차 호출, LLM은 자동 검증만 | 낮음 | 명령어만 |

`/doc-init`은 *대규모 창작 + 정합성 점검 + 외부 자료 조사*가 한꺼번에 일어나므로 *체계적 방법론(=스킬)*의 가치가 크다. 나머지는 *단순 액션 트리거*로 충분.

### 4.3. 명령어별 상세

#### 4.3.1. `/doc-init [문서경로] [ID]`

- **입력**:
  - `[문서경로]`: docs/raw 폴더 내의 사용자 문서 경로 (예: `@docs/raw/강아지형.md`)
  - `[ID]`: 4자리 순서코드. `랜덤` 지정 시 시스템이 자동 생성 (4자리 숫자, 기존 식별코드와 중복 회피)
- **인자 미지정 시 동작**:
  - 인자가 없으면 *docs/raw 폴더 내의 모든 `.md` 파일*을 한 사상체의 컨셉·레퍼런스 자료로 통합 분석. ID는 자동 랜덤 생성.
- **처리**:
  1. docs/raw 문서를 읽어 컨셉·레퍼런스 분석
  2. 사상체_정의.md의 형식·표기·문체에 맞춰 5개 항목 작성
  3. 부족한 정보는 *창작*하거나 *외부 자료 조사*로 보충
  4. `docs/working/<순서코드>/` 폴더 생성, 5개 항목 파일 + 5개 빈 피드백 파일 작성
- **출력**: `docs/working/<순서코드>/` 폴더와 그 안의 10개 파일
- **사용 모델**: Opus

**호출 예**:
```
/doc-init @docs/raw/강아지형.md 1234
/doc-init @docs/raw/강아지형.md 랜덤
/doc-init                              # docs/raw 폴더 전체 + 랜덤 ID
```

#### 4.3.2. `/doc-div <문서경로>`

- **입력**: `docs/entities/사상체_<이름>_v<X.Y>.md`
- **처리** (순수 프로그램):
  1. 사상체 문서의 헤더(`## 개요`, `## 변칙 현상` 등)를 매칭하여 5개 영역 분리
  2. `docs/working/<순서코드>/` 폴더 생성, 5개 항목 파일 + 5개 빈 피드백 파일 작성
  3. 원본 문서를 `docs/entities/archive/`로 이동
- **출력**: `docs/working/<순서코드>/` 폴더
- **사용 모델**: 없음 (프로그램 단독 실행)

#### 4.3.3. `/doc-review <ID>`

- **입력**: `docs/working/<ID>/` 내 5개 항목 파일 + 5개 피드백 파일
- **처리**:
  1. 5개 피드백 파일에서 *처리 대기*(`- [ ]`) 항목들을 수집
  2. 각 피드백에 대해 해당 항목 파일을 갱신
  3. 처리 완료된 피드백을 *처리 완료*(`- [x]`) 영역으로 이동, 처리일 기록
- **출력**: 갱신된 항목 파일 + 정리된 피드백 파일
- **사용 모델**: 현재 모델 (사용자가 `/model`로 사전 선택)

#### 4.3.4. `/doc-ig <ID>`

- **입력**: `docs/working/<ID>/`
- **처리**:
  1. `validate.ts` 실행 — §7.4 자기 점검표 검증
  2. 검증 통과 시 `integrate.ts` 실행 — 5개 항목을 단일 사상체 문서로 통합
  3. 통합본을 `docs/entities/사상체_<이름>_v<X.Y>.md`로 저장
  4. `index-entities.ts` 실행 — `사상체_목록.md` 갱신
  5. `docs/working/<ID>/` 폴더 정리 (삭제 또는 `docs/working/archive/`로 이동)
- **출력**: `docs/entities/`의 새/갱신된 사상체 문서 + 갱신된 사상체 목록
- **사용 모델**: 검증 단계에서만 Sonnet 사용. 통합·인덱싱은 프로그램 단독.

## 5. 프로그램 도구

### 5.1. 도구 개요

| 도구 | 입력 | 출력 | 호출 시점 |
|---|---|---|---|
| `decompose.ts` | `docs/entities/<X>.md` | `docs/working/<ID>/` 10개 파일 | `/doc-div` |
| `integrate.ts` | `docs/working/<ID>/` 5개 항목 파일 | `docs/entities/<X>_v<N>.md` | `/doc-ig` |
| `validate.ts` | `docs/working/<ID>/` 또는 통합본 | 검증 결과 (통과/실패 + 상세) | `/doc-ig` |
| `index-entities.ts` | `docs/entities/` 전체 | `docs/entities/사상체_목록.md` | `/doc-ig` 후 |

### 5.2. decompose — 사상체 문서 분해

**책임**:
- 단일 사상체 문서를 *헤더 매칭 기반*으로 5개 영역으로 분리
- 분리된 영역을 각 항목 파일에 저장
- 빈 피드백 파일 5개도 같이 생성
- 원본 문서를 `archive/`로 이동

**의존 정보**:
- 항목 헤더는 *정확히 다음과 같이* 표기되어야 한다 (헤더 정규화 규칙):
  - `## 개요` (산하의 `### 파생 개체`·`### 설명` 포함하여 통째로 한 파일로)
  - `## 변칙 현상`
  - `## 격리 절차`
  - `## 대응 지침`
  - `## 사건 기록`

**`## 개요` 분해 규칙**:
- `## 개요` 영역 전체(개요 표 + `### 파생 개체` + `### 설명`)를 *그대로* `<ID>_개요.md`에 보존
- frontmatter도 `<ID>_개요.md` 머리에 보존

### 5.3. integrate — 항목 통합

**책임**:
- 5개 항목 파일을 *고정 순서*로 결합
- frontmatter를 `<ID>_개요.md`에서 추출하여 통합본 머리에 배치
- 통합본 파일명은 `사상체_<명칭>_v<X.Y>.md`로 생성
- 버전은 *마지막 archive 버전*을 기반으로 자동 증가 (또는 사용자 지정)

**고정 순서**:
1. frontmatter (`<ID>_개요.md`에서 추출)
2. `# APMB 사상체 문서` 헤더
3. `## 개요` 영역 (`<ID>_개요.md` 본문 — 표 + `### 파생 개체` + `### 설명`)
4. `## 변칙 현상` (`<ID>_변칙현상.md`)
5. `## 격리 절차` (`<ID>_격리절차.md`)
6. `## 대응 지침` (`<ID>_대응지침.md`)
7. `## 사건 기록` (`<ID>_사건기록.md`)
8. 문서 종료 안내문

### 5.4. validate — 정합성 검증

**책임**:
- `사상체_정의.md` §7.4 자기 점검표의 각 항목을 *기계적으로 검증 가능한 형태*로 변환하여 자동 점검
- 검증 항목 (자동 가능):
  - frontmatter 표준 12 필드 충족 여부
  - 본문 4항목 중 최소 1개 존재 여부
  - 인용 표기 §6.4 규칙 (정규식 매칭)
  - `~요` 체 미사용 여부 (정규식 매칭)
  - 영단어 배제 (시스템 명시 대상이 잔존하는지)
  - 검열 비율 5~15% (`█` 또는 `[기밀 분류]`·`[데이터 말소]`·`[기록 보류]` 토큰 빈도)
  - 사건 기록 흔적 최소 1개 존재
- 검증 항목 (자동 불가, *경고 출력*만):
  - 표면/본질 이중 구조 존재 여부 (의미론적 판단 필요)
  - 변칙 현상 §6.3 6요소 권장 골격 (LLM 판단 필요)
  - 관리국 본질 노출 1~2회 (의미론적 판단 필요)

**출력 형식**:
- 통과: `OK: 모든 자동 검증 항목 통과` + LLM 검증이 필요한 *경고 목록*
- 실패: 각 실패 항목의 *위치·이유·제안 수정*

### 5.5. index-entities — 사상체 목록 자동 인덱싱

**책임**:
- `docs/entities/`의 모든 `사상체_*.md` 파일을 스캔
- 각 파일의 frontmatter를 읽어 메타데이터 추출
- `docs/entities/사상체_목록.md`를 *완전 재생성*
- 표 형식: 식별코드 / 명칭 / 위험 등급 / 주요·부차 변칙성 / 보안 등급 / 상태 / 마지막 갱신

**재생성 정책**:
- 기존 `사상체_목록.md`는 *덮어쓰기*. 사용자의 수동 편집은 보존되지 않는다.
- 사용자 수동 편집이 필요한 영역(예: 분류 그룹화·메모)이 있다면 *별도 파일*로 둔다.

### 5.6. 기술 스택

| 분류 | 선택 |
|---|---|
| 언어 | TypeScript |
| 런타임 | Node.js |
| frontmatter 파싱 | gray-matter |
| 마크다운 AST | unified + remark-parse / remark-stringify |
| YAML | js-yaml |
| 파일 시스템 | Node.js 내장 `fs/promises` |
| 실행 방식 | `infra/tools/` 디렉터리에서 `node scripts/<도구>.ts` 또는 npm 스크립트 |

**선택 근거**: 향후 APMB 웹사이트가 Next.js + Fumadocs로 개발될 예정. 동일 언어·동일 라이브러리를 사용하면 *도구의 코드*와 *웹사이트의 콘텐츠 처리 코드*가 모듈 공유 가능.

## 6. LLM 라우팅

### 6.1. 모델별 역할

| 모델 | 주 역할 | 호출 시점 |
|---|---|---|
| **Opus** | 대규모 창작·복잡한 해석 | `/doc-init` 전체 단계. `/doc-review` 시 [창작] 태그 다수일 때 |
| **Sonnet** | 형식·규칙 적용·검증 | `/doc-ig`의 검증 단계. `/doc-review` 시 [정합] 태그 다수일 때 |
| **프로그램** | 순수 기계 처리 | `/doc-div` 전체. `/doc-ig`의 통합·인덱싱. |

### 6.2. 피드백 태그

사용자가 피드백 작성 시 다음 두 태그를 자유롭게 사용한다.

| 태그 | 의미 | 예시 |
|---|---|---|
| `[창작]` | 새 내용 창작·재해석 필요 | `[창작] 변칙 현상 (3)의 임계점이 약함. 더 극단적인 사례 추가.` |
| `[정합]` | 형식·표기·문체 정합화 | `[정합] (4)의 *사상체* 표기를 §6.4.3 형식으로 정합화.` |

### 6.3. 모델 선택 책임

**현재 모델 기반 라우팅**:
- `/doc-review` 명령어는 *호출 시점의 현재 모델*을 사용한다.
- 모델 변경은 사용자가 `/model` 명령어로 *명시적으로* 수행한다.
- 즉 시스템이 *피드백 태그를 보고 자동으로 모델을 바꾸지 않는다*.

**근거**: 자동 모델 라우팅은 *Claude Code 환경의 제약*과 충돌 가능성. 또한 사용자가 *원하는 모델*을 명시적으로 통제하는 것이 *불확실성*보다 낫다.

## 7. 피드백 운영 규칙

### 7.1. 피드백 작성 형식

피드백 파일은 다음 표준을 따른다:

```markdown
# <항목명> 피드백 (순서코드: <ID>)

## 처리 대기

- [ ] [태그] 피드백 내용

## 처리 완료

- [x] [태그] 피드백 내용 — 처리일: YYYY-MM-DD
```

- *처리 대기* 와 *처리 완료* 영역은 *항상 둘 다 존재*해야 한다. 빈 영역이어도 유지.
- 피드백 항목 한 줄은 *체크박스 + 태그 + 본문*의 구조.

### 7.2. 피드백 처리 마킹

- `/doc-review` 실행 시 LLM이 *처리 대기* 영역의 `- [ ]` 항목들을 순회 처리.
- 처리 완료된 항목은 다음 두 변경을 받는다:
  1. 체크박스 `[ ]` → `[x]`
  2. *처리 대기* 영역에서 *처리 완료* 영역으로 이동
  3. 항목 뒤에 ` — 처리일: YYYY-MM-DD` 추가

### 7.3. 처리된 피드백 보관 정책

- *처리 완료* 영역은 *기록 보존*용으로 유지된다.
- 다음 갱신 시 LLM이 이 영역을 *컨텍스트*로 활용 가능 — *이전에 어떤 변경이 어떻게 적용되었는지* 학습.
- 영역이 비대해지면 사용자가 수동으로 *오래된 항목을 제거*할 수 있다 (시스템 강제 없음).

## 8. 사상체 문서 정합성 검증

### 8.1. 자동 검증 항목

`validate.ts`가 자동 점검하는 항목:

| 항목 | 검증 방식 |
|---|---|
| frontmatter 12 필드 충족 | YAML 파싱 후 키 매칭 |
| 본문 4항목 중 최소 1개 존재 | 헤더 매칭 |
| 인용 표기 §6.4 규칙 | 정규식 매칭 (예: `사건기록 \[` 패턴 부재 확인) |
| ~요 체 미사용 | 정규식 매칭 (`요\.`, `요,`, `요\s` 등) |
| 영단어 배제 | 시스템 명시 대상 어휘 잔존 검색 (메커니즘/매트릭스/모니터링/프로토콜) |
| 검열 비율 | 토큰 빈도 측정 후 5~15% 범위 확인 |
| 사건 기록 흔적 | 사건기록.md 내 코드 형식 `[<코드>-<순서>]` 최소 1개 존재 |

### 8.2. 검증 실패 시 대응

- 검증 실패는 *블로커*가 아니라 *경고*. 사용자가 *무시하고 확정* 선택 가능.
- 단 검증 실패 항목은 *확정 명령어 출력에 명시적 표시* — 사용자가 인지하지 못한 채 확정하는 것은 방지.
- LLM이 자동 검증할 수 없는 항목(표면/본질 이중 구조, 변칙 현상 6요소, 관리국 본질 노출)은 *Sonnet에게 점검 요청*하는 별도 단계로 처리.

## 9. 보류 항목 — 향후 결정

### 9.1. 단편 콘텐츠 유통

사용자의 궁극적 목적인 *"격리 절차·대응 지침을 나폴리탄/격리픽션/규칙괴담 장르의 단편 콘텐츠로 유통"*은 본 시스템 v0.2의 범위 밖이다.

**현재까지 검토된 두 해석**:

| 해석 | 설명 |
|---|---|
| A — 사상체 수정 = 콘텐츠 유통 | 격리 절차·대응 지침에 *새 단편 추가*가 곧 콘텐츠 유통. 별도 워크플로우 불필요. |
| B — 단편은 독립 작품 | 사상체 본문은 *일반 규칙*만, 개별 단편은 `docs/entities/<사상체>/contents/` 별도 보관. 별도 워크플로우(Tier 3) 필요. |

**결정 보류 이유**: 단편 유통의 *실제 운용 표면*(어떻게 시청자에게 노출할지, 어떤 빈도로, 어떤 매체로)이 더 구체화된 후 결정해야 한다.

**결정 시점**: 사상체 문서가 *몇 개 이상* 누적되고, 격리 절차·대응 지침의 *콘텐츠로서의 양상*이 실제로 보이기 시작할 때.

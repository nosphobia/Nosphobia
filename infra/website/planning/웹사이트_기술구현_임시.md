# 노스포비아 웹사이트 기술구현 임시 기록

> **본 문서는 *확정이 아닌 임시 기록*이다.** mockup 사이클이 진행되는 동안 등장하는 기술 결정·논의를 한곳에 모아둔다. mockup이 끝나는 시점에 다시 정밀 검토하여 `웹사이트_기술구현_확정.md` (가칭)로 격상시킨다.

## 본 문서의 위치

- mockup 작업 도중 *기술 구현* 관련 결정이 등장하면 → **본 문서를 갱신**한다 (별도 문서 신설 X)
- mockup 사이클이 끝난 시점 → 본 문서를 *재논의·정밀 검토* → 확정본으로 격상
- 본 문서의 결정은 *언제든 변경 가능*하며, 디자인 mockup 결정이 *기술 결정에 영향*을 줄 경우 그 영향이 본 문서에 반영된다

## 본 문서가 다루는 영역

- 프레임워크·라이브러리·아키텍처 패턴의 *임시 결정*

## 1. 사이트의 레이어 구조 (확정 — 기획 v2.0 §2 따름)

본 절은 기획 문서 v2.0 §2의 3 레이어 구조를 *기술 관점*에서 재정리한 것. 기획 결정은 그대로 유지.

```
[OS 레이어 — PC 전용]
  ├─ 부팅 시퀀스 (CLI 인트로)
  ├─ CLI 로그인 / 회원가입
  ├─ Win98 데스크탑 (아이콘·태스크바·시계)
  │    ├─ 관리국 시스템 ← 실제 진입 가능
  │    └─ 내 컴퓨터 / 휴지통 / 메모장 ← 접근 거부 다이얼로그
  └─ 유휴 노이즈·CRT 효과 (대폭)
       │
       │ "관리국 시스템" 아이콘 더블클릭
       ↓
[관리국 시스템 레이어 — PC·모바일 공통]
  ├─ 보안 서약서 (첫 접속 시)
  ├─ 메인 대시보드
  ├─ 본국 안내 / 직무 편람 / 자료실 / 공지
  ├─ 검색 (헤더 우측 상주)
  ├─ 댓글·추천 (사상체 문서)
  └─ 검열 표기·접근 거부·호러 디테일
       │
       ↓ (페이지의 80%)
[문서 레이어 — 통일된 문서 페이지]
  ├─ 공통 문서 레이아웃 (메타 박스·본문·사이드)
  └─ 문서별 커스터마이즈 (노스포비아 = 남보라 침투 등)
```

### 1.1. PC 환경에서의 창 구조 (mockup 사이클 중 결정)

- PC에서 *관리국 시스템* 아이콘 더블클릭 → *드래그·리사이즈·최대화·최소화 가능한 창*이 열림
- 창 안에 *관리국 시스템 레이어 + 문서 레이어*가 풀로 동작
- 창 크기 = 콘텐츠의 viewport (반응형 분기 기준)
- 창의 최소 폭: **1024px** (§3 결정)
- 모바일은 *창 UI 자체를 그리지 않고* 풀스크린으로 인트라넷 본체 진입

### 1.2. 인-유니버스 명분

- *PC 사용자*: 관리국이 IG 등급 탐사자에게 지급한 *정규 워크스테이션*. 외부 인터넷 차단, *관리국 시스템 프로그램*만 정상 동작. 창 크기·OS 설정도 본국이 사전 구성하여 *시청자가 변경할 수 없음*
- *모바일 사용자*: *임시 모바일 접속 모드*. 인트라넷 본체에는 도달 가능하나 워크스테이션 환경은 제공되지 않음

## 2. 임시 기술 스택 (변경 가능)

```
프레임워크:         Next.js (Pages Router)
스타일링:           Tailwind CSS + 98.css (영역 분리)
셸 컴포넌트:        windows-98-ui  ★ 후보 (Tailwind 호환 우선)
                    또는 React95 (styled-components 기반, 보류)
창 관리:            react-rnd  (드래그·리사이즈)
창 안 반응형:       iframe 임베드 또는 container query
상태 관리:          Zustand
영구 저장:          Supabase (계정·서약서 동의·댓글·추천 등)
애니메이션:         Framer Motion
콘텐츠 렌더링:      @next/mdx (검열 표기 커스텀 컴포넌트 포함)
인증:               Supabase Auth + 가짜 이메일 트릭 + 보안 질문
스팸 방지:          Cloudflare Turnstile
효과 레이어:        직접 작성 (캔버스 오버레이)
폰트:              98.css 픽셀 폰트 (OS 레이어) + Pretendard (관리국·문서 레이어)
검색:              Pagefind 또는 Algolia (데뷔 직전 결정)
호스팅:            Vercel + Supabase
모바일 분기:        /intranet 직진 (OS 레이어 우회)
```

### 2.1. 스택 영역 분리 원칙

```
┌─────────────────────────────────────────┐
│ [효과 레이어] 캔버스 오버레이 (전역)        │
├─────────────────────────────────────────┤
│ [OS 레이어] (PC만)                        │
│   - 98.css (외형)                       │
│   - windows-98-ui (컴포넌트)             │
│   - react-rnd (창 관리)                  │
│   - Win98Provider 스코프 격리            │
├─────────────────────────────────────────┤
│ [관리국 + 문서 레이어]                    │
│   - Tailwind (외형)                     │
│   - @next/mdx (콘텐츠)                  │
│   - Supabase (인증·DB)                  │
│   - 모바일·PC 공통                       │

```

**핵심 원칙**: OS 레이어와 관리국·문서 레이어는 *스타일 시스템이 격리*된다. 98.css 스타일이 인트라넷 본체에 새지 않도록 한다.

## 3. mockup 사이클 중 결정된 신규 항목

본 절은 *과거 임시 문서에 없던* 결정으로, 현재 mockup 작업 중에 등장한 것들.

### 3.1. 반응형 분기 수치

| 항목 | 값 | 근거 |
|---|---|---|
| **PC ↔ 모바일 브레이크포인트** | **1024px** | Win98 표준 해상도 1024×768과 일치. 한글 정독 가독성 (40자/줄) 보장 |
| **PC 최소 창 폭** | **1024px** | 창을 더 줄여도 같은 폭 유지. 다단 그리드·데이터 테이블 안정 |
| **PC 최소 창 높이** | **768px** | 함께 1024×768 단위로 묶음 |
| **모바일 본문 최대 폭** | **640px** | 40em (WCAG 1.4.8 한글 정독 기준) |
| **모바일 최소 지원 폭** | **360px** | 안드로이드 표준 최소 |

조사 근거: Tailwind / Bootstrap / Material Design 표준 + WCAG 1.4.8 한글 줄당 자수 권장.

### 3.2. 창 안 반응형 — iframe vs container query

기술적으로 두 가지 패턴이 가능하며, 본 mockup에서는 *어느 것을 택할지 임시 보류*. 디자인 mockup 사이클에서 *시각 결정*이 굳어진 후 기술 결정 단계에서 확정.

**패턴 A — iframe 방식**:
- 관리국 시스템 창 안에 `<iframe src="/intranet/dashboard">` 형태로 임베드
- iframe이 *자체 독립 viewport*를 가지므로 미디어 쿼리(`@media (max-width: 1024px)`)가 *iframe 크기 기준*으로 동작
- 창 리사이즈 → iframe 리사이즈 → 콘텐츠 자동 반응형
- URL 추적 가능 (창 안 URL이 별도로 존재)
- 외부 직접 접근 시 모바일에서도 같은 페이지를 풀스크린으로 보여줄 수 있음

**패턴 B — Container Query 방식**:
- iframe 없이 같은 페이지 내에서 처리
- 창 컨테이너 DOM에 `container-type: inline-size` 지정
- 내부 콘텐츠는 `@container (max-width: 1024px) { ... }` 분기
- 2023년 이후 모든 메이저 브라우저 지원

**잠정 결정**: **iframe 방식 우선 검토**. 이유:
- URL 추적 가능 (트위터 공유·외부 링크 등에서 유리)
- *windows93.net*, *98.js* 등 유사 프로젝트의 표준 패턴
- 코드 재사용 — 같은 페이지가 PC 창 안·모바일 풀스크린 양쪽에 사용 가능

본 결정은 *기술 구현 단계 진입 시 재검증* 필요. 라이브러리 선택에 따라 패턴 B가 더 자연스러울 수도 있음.

### 3.3. 창 UI 라이브러리 후보 비교

mockup 단계 중 *windows 93 / windows 98 js* 등 관련 오픈소스를 조사한 결과:

| 라이브러리 | 라이센스 | 창 관리 | iframe 임베드 | 프레임워크 | 추천도 |
|---|---|---|---|---|---|
| **windows-98-ui** | MIT | windows-98-ui + react-rnd | 가능 (별도 구현) | React + Tailwind | ★★★ |
| **98.css** | MIT | 없음 (CSS만) | N/A | 모두 호환 | ★★★ (위젯 외형) |
| **React95** | MIT | Window 컴포넌트 제공 | iframe 직접 가능 | React 전용 (styled-components) | ★★ (Tailwind 충돌) |
| **OS-GUI / 98.js.org** | source-available | 전부 지원 + iframe | recurseIntoIframes 지원 | vanilla JS | ★ (라이센스 모호) |
| **windows93.net** | 불명 | 자체 구현 | 자체 앱만 | vanilla JS | × (재사용 불가) |

**잠정 결정**: **98.css + windows-98-ui + react-rnd** 조합 (과거 임시 문서 §3.3과 동일 결론). 이유:
- Tailwind와 충돌 없음 (영역 분리 가능)
- 모두 MIT 라이센스
- React95의 *테마 교체 기능*은 우리에게 불필요한 오버스펙

본 결정은 *기술 구현 단계*에서 실제 셋업 후 검증 필요.

### 3.4. 콘텐츠 렌더링 — @next/mdx 유지

과거 임시 문서 §3.7의 *@next/mdx (순수 MDX)* 결정 유지. 이유 재확인:
- 노스포비아 프로젝트의 모든 콘텐츠가 *이미 마크다운으로 작성*되어 있음 (`lore/`, `patterns/`, `docs/entities/`)
- v2.0 §10 *문서 통일 정책*에 따라 콘텐츠의 80%가 통일된 마크업 필요
- 검열 표기(`█`·`[기밀 분류]`·`[데이터 말소]`·`[기록 보류]`)를 *커스텀 컴포넌트*로 깔끔하게 처리 가능

기각된 대안: Fumadocs (과거 임시 문서 §3.7 참조).

## 4. 모바일 분기 전략 (과거 임시 문서 §4 + v2.0 §7.2 통합)

### 4.1. 라우트 구조

```
/              ← PC: Win98 데스크탑 표시 / 모바일: /intranet으로 자동 이동
/intranet      ← 인트라넷 메인 (PC·모바일 공통, 단 PC는 창 안에서 iframe으로 로드)
/intranet/*    ← 모든 위키 문서 (PC·모바일 공통)
```

### 4.2. 구현 방식

- **서버 측 분기**: Next.js `getServerSideProps`에서 user-agent 검사. 모바일이면 `/intranet`으로 즉시 리다이렉트
- **클라이언트 측 보강**: 화면 너비도 추가 검증 (1024px 기준)

### 4.3. 모바일 사용자 경험 (v2.0 §7.2 따름)

- 짧은 부팅 애니메이션 (1~2초, PC의 11초 CLI 인트로 아님)
- 행정 폼 톤 로그인 (CLI 콘셉 아님)
- 보안 서약서 → 인트라넷 본체
- 톤: 행정 양식 톤, *호러 톤의 80% 유지* (검열 표기·CRT 약화·접근 거부 등)

### 4.4. 모바일에서 잃는 것 vs 유지되는 것

| 요소 | 모바일 |
|---|---|
| 부팅 시퀀스 (CLI 11초) | 잃음 → 짧은 부팅 1~2초로 대체 |
| 데스크탑·창 관리 | 잃음 |
| Win98 시각적 외피 | 잃음 |
| 검열 표기 | 유지 |
| CRT·노이즈 오버레이 | 유지 (강도 약간 낮춤) |
| 유휴 효과 | 유지 |
| 접근 거부 페이지 호러 | 유지 |
| 보안 서약서 | 유지 |
| 댓글·추천 | 유지 |
| 검색 | 유지 |

### 4.5. 부가 이점

- *SEO 친화*: 인트라넷 페이지가 정상 URL을 가짐
- *공유 친화*: 시청자가 링크 공유 시 PC는 데스크탑·창 거치고, 모바일은 직진
- *개발 친화*: 개발 중 셸 우회해서 인트라넷만 빠르게 확인 가능

## 5. 인증·계정 임시 결정 (과거 임시 문서 §5 + v2.0 §12 통합)

### 5.1. 가입·로그인 정보 (v2.0 §12.2 확정 따름)

- **사용자명**(노출 닉네임) + **식별자**(계정 ID) + **식별번호**(계정 비밀번호)
- 이메일 *수집·인증 없음*
- 사용자명은 *고유* (중복 불허) + *변경 불가*
  - 인-유니버스 명분: *"등록된 탐사자 식별명은 보안 기록 보존을 위해 변경할 수 없습니다."*
- 식별번호 = *해시 저장 필수* (bcrypt 등)

### 5.2. Supabase 구현 방식 — "가짜 이메일 트릭"

Supabase Auth는 이메일 기반이 디폴트이므로:
- 사용자 입력 식별자 `노스탐사자123`을 내부적으로 `노스탐사자123@apmb.local` 같은 가짜 이메일로 저장
- 사용자에겐 *식별자 폼만 노출*
- Supabase의 인증·세션·JWT 기능은 정상 작동

기각된 대안: *완전 커스텀 인증* (자체 users 테이블 + bcrypt + JWT 직접 발급). 이유: 보안 이슈 가능성↑, 작업 시간 3~5일.

### 5.3. 비밀번호 복구 — 보안 질문 방식 (v2.0 §12.3 따름)

- 가입 시 *비상 식별 문구* 입력 (사용자만 아는 문장)
- 식별번호 분실 시 이 문구로 인증 → 재설정
- 인-유니버스 명분: *"본 단말 등록 시 입력한 비상 식별 문구를 기입하십시오"*

### 5.4. 세션 — 24시간 비활성 만료 (v2.0 §12.3)

- 마지막 활동 기준 24시간 경과 시 자동 로그아웃
- 만료일이 *마지막 활동 + 24시간*으로 갱신되는 영속 쿠키 또는 서버 세션 토큰

### 5.5. 스팸 방지 — Cloudflare Turnstile (필수)

이메일 인증 없는 가입은 *반드시* 봇 방지 장치 필요:
- Cloudflare Turnstile (무료, 보이지 않는 봇 차단)
- 가입·로그인 폼에 통합
- 추가로 Supabase 측 속도 제한 적용

## 6. 영구 저장과 세션 상태의 분리 (v2.0 §13·§14 정합)

### 6.1. Zustand (세션 상태만)

- 현재 어떤 창이 열려 있나, 부팅 시퀀스 진행 상태, 유휴 효과 활성화 등
- 가벼움, LLM 친화도 ★★★

### 6.2. Supabase (영구 저장)

- 계정 정보 (사용자명·식별자·식별번호 해시·가입일·최종 접속일)
- 서약서 동의 필드 (`security_oath_agreed_version`) — v2.0 §13
- 댓글·추천 데이터 — v2.0 §17
- 사상체 일람 권한 신청·심사 상태 — v2.0 §15.2

### 6.3. LocalStorage (비로그인 익명 보조)

- v2.0 §8.1 *비로그인 익명 방문자의 인트로 일일 스킵 보조* — `intro_last_seen_date`
- v2.0 §7.2 모바일 첫 진입 안내 *1회성 알림* — `mobile_notice_acknowledged`

**중요 변경**: 과거 임시 문서 §3.5의 "*영구 저장은 LocalStorage 그대로 유지*"는 **폐기**. v2.0에서 *서약서 동의는 계정 종속*, *인트로 일일 스킵은 계정 최종 접속일 기반*으로 변경됨. LocalStorage는 *비로그인 익명 방문자* 보조에만 사용.

## 7. 효과 레이어 (직접 작성)

라이브러리 미사용 결정. 이유:
- CRT·노이즈·글리치는 *우리 톤에 맞춘 강도·빈도 조절*이 핵심
- 라이브러리는 *일반적 효과* 위주 — 호러 톤 미세 조정에 부적합
- 자체 캔버스 코드(~100줄)가 LLM 보조 작성 가능 분량

mockup 작업 중 굳어진 *5종 CRT 효과* (스캔라인·노이즈·비네팅·스캔빔·미세 깜빡임)와 *글리치 효과*는 [`디자인_기획.md`](디자인_기획.md) §6.1·§6.2로 추출 예정.

## 8. 미결정 영역 (TBD)

### 8.1. 🚧 인-유니버스 OAuth 추가 여부
- 데뷔 후 *디스코드 OAuth* 추가 보류
- 추가 시: 팬 커뮤니티 통합 ↑, 가입 편의 ↑
- 추가 안 함: *이메일 없는 폐쇄적 등록* 톤 강화

### 8.2. 🚧 데스크탑 아이콘 자산 — 공식 vs 자체 제작
- 공식 Win98 아이콘 (라이센스 회색 지대) vs 자체 제작 (일관성 ↑)
- 현재 mockup은 *인라인 SVG 픽셀 아트* 상태. 단계 4 진입 전 자산 자체 제작 또는 라이센스 안전한 공식 자산 도입 결정 필요

### 8.3. 🚧 검색 도구 선택 — Pagefind vs Algolia
- Pagefind: 오픈소스, 빌드 타임 인덱스
- Algolia: SaaS 무료 티어, UI 풍부
- 데뷔 직전 결정해도 늦지 않음

### 8.4. 🚧 창 안 반응형 — iframe vs container query
- §3.2 참조. 라이브러리 선택과 함께 기술 구현 단계에서 최종 확정

### 8.5. 🚧 데이터 백업·운영 정책
- Supabase 무료 티어의 7일 백업만으로 충분한가
- 정기적인 DB 덤프 자동화 필요 여부
- 초기엔 단순하게, 사용자 증가 시 재검토

### 8.6. 🚧 노스포비아 문서의 *남보라 침투* 구현 방식
- v2.0 §10.2 *문서별 디자인 커스터마이즈*의 시각 토큰을 *CSS 변수 오버라이드*로 처리할지, *별도 테마 클래스*로 처리할지
- 디자인 기획에서 *변형 가능한 토큰 범위*가 굳어진 후 결정

## 9. 재논의 방지 메모

다음 항목들은 *이미 충분히 검토되어 결정*되었다. 새 세션에서 별다른 새 정보 없이 재논의하지 말 것:

| 결정 | 재논의 금지 이유 |
|---|---|
| Next.js Pages Router | App Router 검토 후 LLM 친화도·단순성으로 결정 |
| @next/mdx (Fumadocs 아님) | 한 번 Fumadocs로 갔다가 시간 차이가 거의 없고 톤 자유도 우위로 MDX 회귀 |
| Tailwind + 98.css 영역 분리 | styled-components(React95) 검토 후 LLM 친화도·테마 교체 불요로 결정 |
| 가짜 이메일 트릭 | 완전 커스텀 인증 검토 후, 보안·시간 이유로 트릭 선택 |
| 모바일 = OS 레이어 우회 | 셸 강제·모바일 차단·셸 우회 3안 검토 후 결정 |
| 효과 레이어 자체 작성 | 라이브러리 검토 후 호러 톤 조절 자유도로 자체 작성 결정 |
| iframe 우선 검토 (창 안 반응형) | windows93·98.js·React95 조사 후 URL 추적·표준 패턴 기준 결정 |
| 브레이크포인트 1024px | Win98 표준 해상도·한글 정독 가독성·디자인 시스템 표준 조사 후 결정 |

이들 결정을 *바꿔야 할 새 정보*가 등장하면 별도 검토. 그 외엔 본 결정사항 위에서 작업.

# APMB 문서 사이트 디자인 시안 인계 문서

> 이 문서는 노스(사용자)가 다른 세션에서 진행 중인 노스포비아(APMB) 프로젝트 웹사이트 기획에 본 디자인 시안을 적용하기 위해 작성된 인계 자료입니다. 시안 HTML 파일(v3b, v4)과 함께 전달됩니다.

---

## 0. 빠른 안내 — 인계받는 세션을 위해

- **첨부 파일**: `apmb_document_sample_v3b.html`, `apmb_document_sample_v4.html`
- **사이트 내용은 무시할 것**: 노스포비아 사상체 정보(Aj-06-SP-0341 등)는 디자인 테스트용 더미 데이터이며 실제 세계관과 다름. **디자인 구조와 시각 시스템만 참조 대상**.
- **이 시안은 v1 → v2 → v3 → v3a/v3b → v4의 반복 작업 결과물**이며, v3b와 v4가 최종 채택안.
- 사용자가 부분별 수정 요청(드롭다운 추가, 위젯 sticky 고정, 위젯 변경 등)을 할 예정. **§4 부분별 카탈로그**를 참조해 각 컴포넌트의 위치와 의도를 파악 후 작업.
- **§5 자주 발생할 수정 시나리오**에 주요 변경 패턴별 작업 가이드 수록.

## 1. 프로젝트 배경

### 1.1 노스포비아(APMB) 프로젝트 개요
- **프로젝트명**: 노스포비아 (Nosophobia)
- **세계관**: APMB (초상현상관리국 / Anomalous Phenomena Management Bureau) — 이상 현상을 관리하는 가상의 정부기관을 중심으로 하는 픽셔널 유니버스
- **시그니처 컬러**: `#322659` (딥 퍼플)
- **공식 명명 규칙**: APMB-DOC-XXX
- **기술 스택**: React + Tailwind CSS, GitHub 관리

### 1.2 이 디자인 시안의 위치
본 시안은 React/Tailwind 적용 이전의 **순수 HTML/CSS 시각 프로토타입**. 디자인 시스템의 톤·구조·구성요소를 확정하기 위한 단계이며, 다른 세션에서 React 컴포넌트로 변환·통합될 예정.

## 2. 디자인 컨셉과 톤

### 2.1 핵심 컨셉
**"위키피디아/SCP 같은 정통 정부 문서 사이트 + 다크 Y2K/Webcore가 침투한 미학"**

- **베이스 (60~70%)**: 정통 위키 문서 (3단 그리드, 인포박스, 학술적 섹션 번호, 표 기반 메타데이터)
- **주변부 침투 (30~40%)**: 다크 Y2K/Webcore (시스템 바, CRT 위젯, 픽셀 아이콘, 글리치, Win98 다이얼로그, 88x31 배너)

### 2.2 톤 핵심 원칙
- **본문은 깔끔하고 권위적**: 본문 영역 자체는 위키 수준의 가독성 유지
- **주변부는 살아있는 시스템**: 헤더·사이드바·인포박스·푸터는 계속 무언가가 일어나고 있다는 인상
- **카와이/장식적 요소는 배제**: 하트, 무지개, 산리오, 형광 핑크 강조 같은 Webcore의 친밀한 요소는 모두 제거
- **다크하고 으스스한 보라 톤 유지**: 시그니처 #322659가 모든 시각 결정의 기준

### 2.3 두 가지 모드(전략적 분리)
초기 분석에서 정립된 핵심 전략:

- **Mode A (평상시 APMB)**: 깔끔한 정부 문서 + 절제된 시스템 어휘
- **Mode B (사상체 침투)**: 글리치/디스토션/가짜 다이얼로그 폭발

**현재 v3b는 Mode A에 가깝고, v4는 Mode A와 B의 중간 지점**. 사상체별 침투 페이지를 만들 때는 v4 베이스에 글리치를 추가로 폭발시키면 됨.

## 3. 두 최종 시안 비교

### 3.1 v3b — 보수적 통합안
**컨셉**: 위키 베이스 + Win98 베벨 + 픽셀 가미 (Webcore 어휘 약 30~40%)

**핵심 추가 요소**:
- 모든 다이얼로그 박스(record, system-notice, toast)에 Win98 클래식 4면 베벨 적용
- 페이지 하단 Win98 작업 표시줄 (Start 버튼 + 열린 창 3개 + 시스템 트레이 + 시계)
- 콘텐츠 헤더 제목 옆 큰 픽셀 문서 아이콘
- 인포박스 헤더의 픽셀 아이콘 (모니터, 자물쇠)
- 첨부 자료 박스의 픽셀 파일 아이콘 3개

**사용 권장 상황**:
- APMB 평상시 페이지 (정상 작동하는 시스템)
- 차분한 정보 전달이 우선인 페이지 (부서 안내, 정책 페이지 등)
- 가독성과 권위가 가장 중요한 페이지

### 3.2 v4 — Webcore/Y2K 본격 강화안
**컨셉**: v3b + 아날로그 호러 + Webcore 위젯 + 추가 픽셀 요소 (Webcore 어휘 약 60~70%)

**v3b 대비 추가된 요소**:
- 페이지 전체 VHS 트래킹 라인 (13초마다 한 번씩 흐름)
- §2 본문의 미식별 캡처 증거 박스 (호러 포인트: SEEN 플래시 + 자기참조 라인)
- 헤더 픽셀 별 5개 (각자 다른 타이밍으로 깜빡임)
- 사이드바 신규 위젯 2개: NOW BROADCASTING (CRT) + 방문자 카운터 (7-segment)
- 사이드바 목차 메뉴 9개 모두에 픽셀 아이콘
- 본문 픽셀 별 분리자 2개
- 푸터 위 88x31 웹배너 줄 (12개)
- 좌측 하단 PIP 떠다니는 미니 모니터
- 부팅 시퀀스 강화 (1.6초 → 2.2초, 5줄 추가)

**사용 권장 상황**:
- 사상체 데이터베이스 메인 페이지
- 침투 현상이 관측되는 페이지
- 분위기·임팩트가 정보 전달만큼 중요한 페이지
- 메인 페이지 (방문자에게 톤을 각인시켜야 하는 곳)

### 3.3 어느 쪽을 베이스로 갈지
**추천**: 사이트 전반의 **베이스 시스템은 v3b**, **사상체 데이터베이스/사건 기록 페이지는 v4**. 페이지 종류에 따라 두 시스템 사이를 오가는 방식이 가장 유연.

## 5. 자주 발생할 수정 시나리오 가이드

### 5.1 메뉴 드롭다운 추가
**현재 상태**: `.main-nav a` 6개가 평평한 텍스트 링크.

**드롭다운 추가 시 권장 구조**:
```html
<nav class="main-nav">
  <a href="#">메인</a>
  <div class="nav-item active">
    <a href="#">사상체 데이터베이스 ▾</a>
    <div class="submenu">
      <a href="#">위험 등급 별 보기</a>
      <a href="#">분류 코드 별 보기</a>
      <a href="#">최근 갱신</a>
    </div>
  </div>
  <!-- ... -->
</nav>
```

**CSS 추가 권장 패턴**:
- `.submenu`는 절대 위치, 헤더 보라 톤 유지
- `.nav-item:hover .submenu { display: block }`
- 호버 시 살짝 글리치 효과 추가 가능 (RGB 색수차 등 Y2K 어휘 유지)
- 서브메뉴 항목에도 픽셀 아이콘 권장 (사이드바 목차 패턴 재사용)

### 5.2 위젯 스크롤 시 고정 (sticky)
**적용 권장 위젯**: 식별 카드, 변칙성 강도 게이지

**구현 방법**:
```css
.infobox-column {
  /* 기존 스타일 유지 */
  align-self: start; /* 그리드 안에서 위로 정렬 */
}

.infobox-column .infobox:first-child,
.infobox-column .anomaly-gauge {
  position: sticky;
  top: 22px; /* 헤더 아래 여백 고려 */
}
```

**주의**:
- 인포박스 컬럼 전체를 sticky로 만들면 사이드바보다 길어질 때 어색함
- 식별 카드만 sticky로 하는 것이 자연스러움 (가장 핵심 정보)
- 모바일(1100px 이하)에서는 인포박스가 숨겨지므로 영향 없음

### 5.3 위젯 추가/제거/이동
모든 사이드바 위젯과 인포박스 위젯은 **독립된 HTML 블록**. 통째로 잘라내거나 다른 위치로 이동 가능. CSS 클래스는 그대로 유지됨.

**예시 — NOW BROADCASTING 위젯을 인포박스 컬럼으로 이동**:
1. `<div class="broadcast-widget">...</div>` 통째 잘라내기
2. `.infobox-column` 안 원하는 위치에 붙여넣기
3. 너비가 자동으로 인포박스 컬럼 폭(300px)에 맞춰짐

### 5.4 색상 톤 변경
**모든 색상은 `:root` 변수로 관리** (CSS 상단). 시그니처 컬러 한 줄만 바꿔도 사이트 전체 톤이 일관되게 변경됨.

```css
:root {
  --bg-header: #322659;        /* 시그니처 딥 퍼플 */
  --accent: #4a3b7a;           /* 액센트 */
  --accent-bright: #6849bb;    /* 링크 */
  --accent-glow: #8b6dc7;      /* 글리치/별 */
  /* ... */
}
```

**주의할 변수**:
- `--terminal-green`, `--terminal-amber`, `--terminal-cyan`, `--terminal-magenta`: 시스템 메시지·글리치용. 톤이 바뀌면 같이 조정 권장
- `--censor`, `--warning`: 검열·경고 표시. 사이트 일관성을 위해 마지막에 조정

### 5.5 페이지 종류별 모드 전환
**Mode A (v3b 베이스) → Mode B (v4 강화) 사이의 전환**:

v3b에 다음을 추가하면 v4가 됨:
1. `.vhs-tracking` div 한 줄 추가
2. `.broadcast-widget`, `.visitor-counter` 위젯 추가 (사이드바)
3. `.evidence-block` 박스 추가 (본문 §2 다음)
4. `.web-rings` 추가 (작업 표시줄 전)
5. `.pip-monitor` 추가 (body 끝)
6. `.pixel-divider` 추가 (섹션 사이)
7. 사이드바 li에 픽셀 아이콘 SVG 삽입

v4에서 다음을 빼면 v3b가 됨:
- 위 모든 요소 제거
- `.glitch-text` 효과는 보존 가능 (취향에 따라)

**페이지별 권장 모드**:
- 메인 페이지: v4 (첫 인상이 중요)
- 사상체 DB 메인: v4
- 사상체 개별 문서: 위험 등급에 따라 분기 (Aj/Bh 등 위험 시 v4, Ks 등 안정 시 v3b)
- 부서 안내·정책·자료실: v3b
- 사건 기록: v4 (서사적 임팩트)

### 5.6 글리치 강도 조정
**핵심 글리치 효과 위치**:
- `.glitch-text` — 제목 RGB 색수차 (현재 4초마다 한 번 0.4초)
- `.frame-flash` — 캡처 박스 SEEN 플래시 (11초마다 한 번)
- `.evidence-block .self-ref` — 자기참조 라인 펄스

산만하다고 느껴지면 `animation-duration`을 늘리거나 `animation-iteration-count: 1` (한 번만)로 변경.

### 8.1 페이지 그리드

## 9. 작업 시 권장 흐름

### 9.1 새 페이지 만들 때
1. 페이지 종류 결정 → Mode A(v3b) 또는 Mode B(v4) 선택
2. 시안 HTML에서 페이지 골격(헤더·푸터·그리드) 복사
3. 본문만 새로 작성. 사이드바/인포박스는 페이지에 맞게 위젯 선별
4. CSS 변수는 그대로 사용. 페이지별 색상 조정 시 변수 추가

### 9.2 위젯 단위 작업 시
1. **§4 부분별 카탈로그**에서 해당 위젯의 CSS 클래스 확인
2. CSS는 클래스 이름으로 검색 (예: `.broadcast-widget`)
3. HTML 블록 전체를 단위로 다루기 (잘라내기/복사/이동)
4. 위젯 간 의존성 없음 — 자유롭게 추가/제거 가능

### 9.3 색상·톤 조정 시
1. `:root` CSS 변수만 수정
2. 개별 색상 하드코딩 지양 (이미 시안에 일부 하드코딩 있으니 발견 시 변수화 권장)
3. 시그니처 컬러 #322659는 보존 권장 (전체 톤 기준점)

### 9.4 React/Tailwind 변환 시
- 각 위젯이 자연스럽게 컴포넌트 단위로 분리됨
- CSS 변수는 Tailwind의 `theme.extend.colors`로 옮기기
- 애니메이션(@keyframes)은 Tailwind config 또는 별도 CSS 모듈
- SVG 픽셀 아이콘은 React 컴포넌트로 추출 권장 (`<PixelIcon name="folder" />`)

## 10. 디자인 결정의 사유 (참고)

### 10.1 왜 다크 Y2K였나
초기 레퍼런스 분석에서 사용자가 제공한 10장의 비주얼은 대부분 Y2K/Webcore 미학이었음. 그중 카와이 계열은 APMB의 관료적 권위와 충돌하므로 배제하고, **다크 Y2K 계열의 어휘만 추출**:
- 윈도우 다이얼로그 콜라주
- 파일명 메타포 (.exe, .log 등)
- 글리치·디스토션
- 픽셀·비트맵 텍스처
- 위젯 패널화
- 다크 유머 시스템 메시지

### 10.2 왜 본문은 절제하고 주변부만 강화했나
완전 글리치/Y2K로 가면 가독성 손실 + SCP 같은 "정통 문서" 정체성 손실. 본문이 정상적으로 작동해야 침투의 충격이 살아남. **본문 = 정상, 주변부 = 살아있는 시스템**의 대비가 핵심.

### 10.3 왜 두 시안(v3b, v4)을 모두 채택했나
페이지 종류에 따라 적절한 강도가 다름. 모든 페이지를 v4로 가면 피곤하고, 모든 페이지를 v3b로 가면 임팩트 부족. **두 시스템을 갖고 페이지별로 선택**하는 것이 가장 유연.

## 12. 이전 작업 세션에서의 핵심 맥락

다른 세션이 사용자와 대화할 때 참고할 만한 사항:

- **사용자의 작업 톤**: 진지하고 구조적. 카와이·가벼움보다 신중한 분위기 선호
